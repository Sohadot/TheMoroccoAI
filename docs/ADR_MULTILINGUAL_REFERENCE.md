## Context

TheMoroccoAI.com publishes one evidence-based reference in English:
- **Data:** canonical evidence, ontology and gaps in `data/`.
- **Pages:** generated by `tools/build.py`, plus a hand-maintained homepage and evaluation page.
- **Hosting:** served as static files by GitHub Pages behind Cloudflare.

TMA-DEC-003 (accepted) makes English authoritative and French and Arabic the next localization priorities. It also requires that:
- original-language excerpts stay intact;
- translations are distinguished from quotations;
- terminology is canonical;
- `hreflang` is correct;
- incomplete translations are never indexed.

The owner wants Arabic- and French-speaking audiences in Morocco to be able to find and read **the same reference**, without a second body of research.

The Sprint 19A audit (Arch §1) found:
- **Hash-bound data:** the canonical files are bound by SHA-256 into `registry/reference-state.json`, the manifest and the published consumer, so storing translations inside them would register as a data change.
- **English-only generator and gates:** templates, dates (`strftime("%B")`), site gates and the state-page linter all assume English.
- **CSS direction:** the CSS is mostly physical (left/right).
- **Fonts:** the bundled Arabic font covers Arabic but is used only on the homepage, and no bundled font covers Tifinagh.
- **Publicly served repository:** every file on `main` can be fetched from the production domain.

## Decision

1. **Single research source.** Evidence, ontology, gaps, changelog and reference state stay in English in `data/` and are never duplicated or altered per language. No language may introduce evidence, entities, classifications, conclusions or interpretations.
2. **Separate translation layer.** Translations live in `i18n/`, outside `data/`, the manifest and `REFERENCE_INPUTS`. There is one language registry and one glossary. Message catalogs cover interface and page strings, and content catalogs cover canonical prose fields keyed by identifier and field. Each translation unit records the SHA-256 of its English source and its review provenance.
3. **Derived pages.** Localized pages are rendered by the same `build.py` functions from the same data, with numbers, dates, identifiers, URLs and links filled in as placeholders from canonical data. Generation is deterministic and covered by `build.py --check`.
4. **Publication rule.** A page is generated in a language only when every unit it needs is approved by two human reviews (substantive and linguistic) and matches the current English source. *(Amended by TMA-DEC-008: one documented human approval, with risk-based escalation; see [TRANSLATION_REVIEW_POLICY.md](TRANSLATION_REVIEW_POLICY.md).)* There is no partial page, English fallback text or placeholder route. Stale or missing translations withdraw the localized page and never block English.
5. **Routing.** English stays at `/`. Arabic is at `/ar/…` and French at `/fr/…`, mirroring English paths. Darija (`/ary/`) and Amazigh (`/zgh/`) are reserved for a later wave (owner decisions Q1 and Q7 below).
6. **SEO.**
   - Every page has a self-referencing canonical.
   - Reciprocal `hreflang` covers only generated equivalents, with `x-default` pointing to English.
   - Every published URL is in the sitemap and no unpublished URL is.
   - Localized titles and descriptions are reviewed text.
   - There is no automatic language redirection.
7. **Authority notice.** Every localized page states that it translates the English reference, that English prevails, and links to the English equivalent. Each also carries the localized ownership and independence disclosures required by TMA-DEC-001.
8. **Out of scope for translation (initial waves).**
   - `/evaluation/` stays English until its task wording passes a separate neutrality review and `docs/EVALUATION_SPEC.md` is amended.
   - `/registry/state/` and `/data/` stay English.
   - JSON outputs are never localized.
   - `source_excerpts` are never altered, and are not translated in the first two waves (Q6).

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| **A. Translation fields inside canonical data** (e.g. `summary_ar` in `ontology.json`) | Changes canonical hashes, the reference snapshot, the manifest and consumer-visible data on every translation edit. Blurs research and translation authority. The existing `domain_labels_ar` is left as a pre-existing exception and is not extended |
| **B. Hand-written copies of pages per language** | Duplicates structure and content and creates divergence, with no machine-checkable link to the English source. Contradicts the single-source requirement |
| **C. Client-side translation (JavaScript, or a third-party translation widget)** | Not indexable as distinct pages. Adds runtime code and, for widgets, third-party requests, contradicting the privacy commitments. Unreviewed output |
| **D. Separate subdomains (`ar.themoroccoai.com`) or separate repositories** | Needs DNS and hosting changes and splits the source. No benefit over subdirectories for one static site |
| **E. Query-parameter or cookie-based language** | Not reliably indexable, needs runtime logic, and is not supported by static Pages |
| **F. `/en/` prefix for English** | Would move every existing URL. Static Pages cannot issue HTTP redirects, so backlinks and indexing would break |
| **G. Publish partial translations with English fallback, marked `noindex`** | Produces mixed-language pages that are thin or misleading. TMA-DEC-003 already forbids indexing incomplete translations, and non-indexed partial pages add maintenance with no audience benefit |

## Rationale

- **Fit with policy and data:** this design satisfies TMA-DEC-003 and the owner's single-source requirement without touching canonical data or existing English URLs.
- **Machine-checkable integrity:** placeholders, source hashes and page-pair parity make number, identifier, date, classification and qualifier integrity checkable by machine.
- **Human judgment where it matters:** automated checks cannot establish semantic equivalence, so human review stays mandatory.
- **Low complexity:** the design keeps the current operating model of static hosting with no runtime code or server logic.

## Consequences

- **Positive:**
  - Arabic and French readers get the same reference with the same identifiers and citations.
  - Translations can be audited against their English source.
  - Stale translations are detected automatically.
  - English releases stay independent.
- **Costs:**
  - A refactor of `build.py`: string extraction and explicit date formatting.
  - Homepage templating, with its inline CSS moved to a stylesheet.
  - CSS converted to logical properties.
  - New gates and tests.
  - A recurring review workload, about 13,400 words of canonical prose for full reference coverage, plus interface and page text.
- **Operational:** a data or English-text change can withdraw localized pages until they are re-reviewed. Pull requests show this before merge.
- **Public statements:** "AR, FR, TZM planned" must be updated in the same change that publishes a language.

## Risks
See the plan's risk register (R1–R10). The highest-impact risks, and their main controls, are:
- **Meaning drift in translation (R1):** controlled by parity gates and human approval (two reviews under TMA-DEC-007; since TMA-DEC-008, one documented human approval with escalation to a second reviewer when a risk criterion applies).
- **Unreviewed text in production (R2):** controlled by keeping drafts off `main` and building from approved units only.
- **Evaluation comparability (R9):** controlled by keeping the evaluation English-only.

## Reversibility

- **Per language:** reversible. Set the language to `withdrawn` (or remove it) in `i18n/languages.json` and rebuild. Its tree, sitemap entries and `hreflang` links disappear, and English pages lose their alternates.
- **Data and URLs:** canonical data and English URLs are never touched, so rolling back cannot affect the reference.
- **Refactors:** the 19B refactors (string extraction, homepage templating, logical CSS) are provably output-neutral for English and can be kept even if localization is abandoned.

## Security and privacy implications

- **Runtime surface unchanged:** no JavaScript, cookies, storage, redirects or third-party requests, and fonts stay self-hosted.
- **Bidirectional spoofing:** text-direction control characters are rejected in catalogs and NFC normalization is enforced.
- **Drafts:** never committed to `main`, because every file there is publicly served.
- **Reviewer identity:** reviewers are recorded pseudonymously by default (TMA-DEC-006).
- **Machine translation:** if used as a drafting aid, it receives only already-public content.

## SEO implications

- **Indexable translations:** each published translation is a separate indexable URL with a self canonical. Translations are not consolidated into English.
- **`hreflang`:** clusters are reciprocal and only include generated pages, with `x-default` pointing to English.
- **No thin or duplicate pages:** there are no placeholder or partial pages, so localized pages are neither thin nor duplicates.
- **Arabic search:** discoverability relies on reviewed, natural titles and descriptions and on approved localized entity names (official names cited where possible). The canonical French `alt_names` stay visible, which helps mixed French/Arabic searches.
- **No claims:** this ADR makes no claims about search volume or rankings.
- **Unverified for later languages:** whether search engines honour `hreflang` for `ary` and `zgh` (ISO 639-3) must be checked before Sprint 19D.

## Testing requirements

- **Existing checks:** English tests and gates stay unchanged.
- **New gates (Arch §9), each with a negative fixture test:**
  - catalog schema;
  - staleness;
  - placeholder, digit, identifier, citation, classification, date, number and qualifier parity;
  - glossary terms and forbidden variants;
  - no English leakage;
  - localized disclosures;
  - `lang`/`dir`/canonical/`hreflang`/`x-default`/`og:locale`;
  - sitemap;
  - per-language forbidden wording;
  - bidi isolation;
  - an RTL layout test;
  - a guard against generating `/<lang>/evaluation/`.
- **Refactor steps:** each must prove the English output is byte-identical (`build.py --check`, 0 stale), or, for the homepage, has identical DOM text and identical screenshots.

## Implementation status

- **Sprint 19B-1 (foundation):** the `i18n/` layer (language registry, English source catalog, empty Arabic and French catalogs, glossary), `tools/i18n.py` (source fingerprints, validation, staleness and orphan report, publication eligibility), English shell and date strings read from the catalog with byte-identical output, and site gates for language routes and `hreflang`. **No translation exists, no review has taken place, and no localized page or route is published.**
- **Sprint 19B-2 (rendering engine):** localized rendering for `ar` and `fr`, strict translation lookup with no English fallback, page publication gates (identifiers, source URLs, numbers and dates, classifications, qualifiers, disclosures, right-to-left isolation, untranslated English), reciprocal `hreflang` / `x-default` / `og:locale` / JSON-LD language and sitemap entries, a no-JavaScript language switcher, withdrawal of files no longer generated, and logical and Arabic CSS with English pixel-identical (Arch §14). No page is registered for localization, so nothing is generated or published.
- **Sprint 19B-3 (reference content extraction):** all presentation text of `/registry/` and `/methodology/` read from the catalog, with English byte-identical. Canonical text (entity names and statuses, classification definitions, domain labels) is resolved from `data/` as content units. There are page requirement sets, a pseudo-localization completeness check, and structural and qualifier-presence gates. The canonical changelog records on `/methodology/` are deferred (Arch §15). Neither page is registered for localization.
- **Sprint 19B-4 (homepage, identity, governance):** the homepage is generated from a catalog-driven template with English byte-identical; changelog and attribute texts have stable identities in explicit maps, so `/methodology/` has no deferred text; and TMA-DEC-008 replaces the two-review requirement with one documented human approval, risk-based escalation and a public translation-policy disclosure (Arch §16). No reviewer is registered, no translation exists and no page is registered for localization.
- **Later sprints:** as in [MULTILINGUAL_IMPLEMENTATION_PLAN.md](MULTILINGUAL_IMPLEMENTATION_PLAN.md).

## Owner decisions (2026-11-22)

The Sohadot integration authority resolved the nine approval questions of the proposal as follows. They are authoritative and are recorded in TMA-DEC-007.

1. **Q1, language strategy.**
   - English remains the sole authoritative research language.
   - Modern Standard Arabic (`ar`) and French (`fr`) are the first publication languages.
   - Moroccan Darija (`ary`) and Standard Moroccan Amazigh (`zgh`) are future localization priorities.
   - Spanish remains a possible future expansion language, without a publication commitment.
   - No localized language may introduce independent research conclusions or duplicate canonical evidence.
2. **Q2, acquisition page.** `/acquisition/` may be localized. Its localization follows the core reference pages and is not part of the initial three-page rollout. Its commercial wording requires a dedicated substantive and legal review before publication.
3. **Q3, reviewers.** *(Review requirements superseded by TMA-DEC-008 on 2026-11-22; the text below is kept as decided. Pseudonymous provenance still applies.)*
   - Each published translation requires two review functions: substantive accuracy and linguistic quality.
   - Reviewers are independent of the drafter.
   - Two different reviewers are preferred; one reviewer may perform both functions only if they did not draft the text.
   - Public review provenance uses pseudonymous identifiers. No personal information is exposed.
4. **Q4, staleness.** No grace period, including for interface strings. Stale content cannot remain published as if current. English publishing remains independent of translation readiness.
5. **Q5, Arabic typography.** Begin with the existing self-hosted Arabic font (Noto Kufi Arabic). Add another self-hosted font only if testing shows a genuine readability need. English typography is preserved.
6. **Q6, source excerpts.** Excerpts stay verbatim in their original language. They are not translated during the first two implementation waves, and a translation is never presented as an original quotation.
7. **Q7, Darija and Amazigh.** Darija initially uses Arabic script. Standard Moroccan Amazigh uses Tifinagh. Both require controlled terminology and competent linguistic review before publication. No premature publication or placeholder routes.
8. **Q8, search-engine verification.** Appropriate search-engine webmaster tools may be used to assess indexing and discoverability. Any account connection, ownership verification or DNS change is a separate operation that needs its own authorization. No invasive tracking or analytics.
9. **Q9, machine-assisted translation.** Machine translation may be used to prepare drafts of already-public content. It cannot substitute for the human substantive and linguistic reviews *(since TMA-DEC-008: for the documented human approval)*. Public documentation explains the translation and review policy accurately, and no review is claimed unless it actually took place. Each translation unit records its `draft_method` (`human` or `machine-assisted`).

## Original approval questions (Sprint 19A, for the record)

These were the questions put to the owner in the proposal. The decisions above answer them.

- **Q1. Language set.** TMA-DEC-003 names "Tamazight and Spanish" as later languages. The Sprint 19A brief names Darija (`ary`) and Standard Moroccan Amazigh (`zgh`) and omits Spanish.
  - Should TMA-DEC-003 be amended to add Darija, keep Amazigh as `zgh`, and drop Spanish (or keep it)?
- **Q2. Acquisition page.** Should `/acquisition/` be translated in wave 1 (19B), or stay English?
  - It is commercial rather than reference content, and its wording is governed by tests.
- **Q3. Reviewers.**
  - May one person perform both the substantive and linguistic reviews (never the drafter) in wave 1?
  - Should reviewers be recorded pseudonymously in the public repository (proposed default) or by name?
- **Q4. Staleness grace.** Should stale `interface` units (navigation and labels only, never research content) be allowed a short grace period? Proposed default: no grace period.
- **Q5. Arabic body typeface.** Keep Noto Kufi Arabic, the bundled font, for Arabic body text, or add a self-hosted Naskh-style face for long reading?
  - Adding one means a new font asset (OFL) and a larger page weight for Arabic pages.
- **Q6. Source excerpts.** Should labelled, non-authoritative translations of `source_excerpts` ever be shown beside the verbatim original? Proposed: not in waves 1–2.
- **Q7. Darija and Amazigh.**
  - Which script for Darija: Arabic, or Latin as well?
  - Should Amazigh be in Tifinagh only?
  - Who provides linguistic review for each?
  - (Sprint 19D prerequisite.)
- **Q8. Webmaster tools.** Should search-engine webmaster tools be verified for the domain, to observe indexing of localized pages?
  - This is an owner action involving third-party accounts. DNS TXT verification would avoid any change to page markup.
- **Q9. Machine translation.** May machine translation be used as a drafting aid, always followed by both human reviews? Should its use be disclosed publicly?
